# ADR-005: dbt for the PIX warehouse

- Status: accepted
- Date: 2026-11-24

## Context

v0.2 and v0.3 built the star schema and the CDC current-state tables as one SQL file per model, run by DuckDB. v0.4 rendered those files as Athena views (`transform/athena/views.sql`) and created the Glue databases and the workgroup. v0.5 was the planned port to dbt. The grain, the `N/D` municipality, and the LSN ordering do not change. What changes is the tool that owns the DAG, the tests, and the docs.

Two adapters are in play. Local and CI have no AWS account, so they need an engine that reads the Parquet zone in place. The deployed path is the v0.4 Athena workgroup over Glue partition projection. A third adapter, or a warehouse that copies the raw zone into Postgres, would throw away both.

The current-state tables are a merge of a log. A full refresh is correct and matches the legacy SQL. An incremental merge is what a later orchestrator will want, and it is only correct if a late file cannot overwrite a newer LSN.

## Decision

dbt is the transformation layer `make model` and `make dq` run. The legacy SQL stays in the repository as the parity oracle.

- `dbt-core` with `dbt-duckdb` is the default target and the CI target. It reads the same raw zone as v0.2. `PIX_RAW_SOURCE=local` uses `PIX_RAW_ROOT`. `PIX_RAW_SOURCE=s3` uses httpfs, path-style when `AWS_ENDPOINT_URL` is a LocalStack URL, virtual-hosted on real AWS. Sources declare `external_location` as `read_parquet(getvariable(...))`. A DuckDB plugin sets the file list on every cursor. An empty glob reads a zero-row sentinel with the writer schema, so a build with no CDC files still produces the seeded dimensions.
- `dbt-athena-community` is the `athena` target. The workgroup default is `pix-data-dev`, the Terraform name `${name_prefix}-${environment}`. `PIX_ATHENA_WORKGROUP`, `PIX_ATHENA_STAGING_DIR`, `PIX_ATHENA_DATA_DIR`, and `PIX_GLUE_PREFIX` override it. Schemas are `pix_staging`, `pix_intermediate`, `pix_marts`, and `pix_seeds`, matching the Glue databases from v0.4. Sources are the Glue external tables in `pix_raw`. `skip_workgroup_check` is on so `dbt parse --target athena` does not call AWS. CI does not run this target.
- Layers stay seeds, staging, intermediate, marts. On DuckDB, staging and intermediate are views and the star-schema marts are tables. On Athena they are views, because the catalog is Hive Parquet with partition projection. Iceberg would be required for a merge table, and v0.4 did not create Iceberg tables. `dbt build --target athena` is the deploy step that replaces running `transform/athena/views.sql` by hand.
- `cur_pix_key`, `cur_pix_transaction`, and `cur_pix_dispute` are incremental on DuckDB. `unique_key` is `id`. `incremental_strategy` is `delete+insert`. The intermediate model still ranks the whole log by `lsn_ord` and keeps deletes. The incremental select writes a key only when that winner's `lsn_ord` is greater than the value stored on the table. A file that arrives late with an older LSN does not replace the row. Arrival order and `commit_ts` are not the order. When the winning `op` is `delete`, the select omits the key and a post-hook deletes it. The stored `lsn_ord` column is the merge state. It is not in the legacy mart. The other columns match. Athena keeps the same select as a view (a full refresh), because there is no Iceberg table to merge into.
- Tests: `schema.yml` describes every model and column. Generic tests are `unique`, `not_null`, `relationships`, and `accepted_values` on the seed code lists. Singular tests are the grain and non-negative checks from `make dq`, the `Não informado` municipality, one name per ISPB on the latest snapshot, and the current-state checks that are not a single column (ISPB width, dispute reason). Source freshness on the three BCB sources uses the partition month, which is the same checkpoint the ingestion watermark stores. The watermark JSON is not a source: fixture builds do not write it, and the nested object is not a table. CDC sources use `commit_ts`. `dbt source freshness` is not in CI, because a fixture month can sit still for weeks. An exposure named `pix_metabase` is the placeholder for the v1.0 dashboard.
- `transform/sql` is kept. `tests/test_dbt_parity.py` builds it and the dbt project on the same fixture Parquet and compares rows. Deleting the SQL in this slice would delete the oracle the parity test runs. `transform/athena/views.sql` is kept for the same reason: `python -m transform.athena_sql --check` still diffs the renderer, and CI cannot execute the Athena target. The supported way to publish models to Glue is `dbt build --target athena`. The script is the legacy render, not the source of truth.

`make dbt-deps`, `make dbt-build`, and `make dbt-docs` are the direct dbt entrypoints. `dbt build` on the fixture Parquet runs in CI next to pytest. `.github/workflows/dbt-docs.yml` is `workflow_dispatch`. It generates the docs site and publishes GitHub Pages when the repository has Pages enabled for Actions.

## Alternatives considered

- Delete `transform/sql` and `views.sql` in this slice and keep only dbt. That is the end state. It is not this slice, because the parity test needs a second implementation to execute, and the Athena contract test needs the rendered script while CI has no Glue catalog. The ADR records dbt as the source of truth for `make model` and for a deploy. The files that remain are the oracle and the checked legacy script.
- Use `dbt-athena` only, and run DuckDB as a DuckDB-attached Athena workaround. Local and CI would then need AWS, which v0.1 ruled out.
- Materialize `cur_*` as `merge` into Iceberg. DuckDB can merge. The v0.4 tables cannot. `delete+insert` plus the LSN predicate and the delete hook is the strategy that works on the DuckDB file without a new table format.
- Incremental facts on `ano_mes` for the three-month revision window. The facts are small and the legacy runner rebuilds them. A partial month delete (a partition removed from raw) is easier to get wrong than a table rebuild. They stay tables on DuckDB and views on Athena.
- Filter incremental CDC with `dt >= max(dt) - lookback`. That misses a file whose commit date is older than the watermark and whose LSN is newer, and it applies a file whose LSN is older when the date is inside the window. The predicate is `lsn_ord`, compared per id, against the image already stored.
- Put dbt in the main `dependencies` list. The Lambda zip is already close to the unzipped limit. dbt is a dev extra. `make` and CI install `.[dev]`.

## Consequences

- `pip install -e '.[dev]'` is required for `make model`. The Lambda build script does not install that extra.
- The first DuckDB build of `cur_*` is a full refresh. The next `dbt run` is incremental. `dbt run --full-refresh` rebuilds from the log and must match the legacy mart apart from `lsn_ord`.
- `dbt source freshness` warns when the newest BCB month is older than 45 days and errors after 120. It warns when the newest CDC commit is older than 2 days. An empty sentinel has no rows, so freshness has nothing to age. Do not fail a build on that.
- Athena schemas are prefixed. A query written for DuckDB `marts.fct_transacoes_mensal` is `pix_marts.fct_transacoes_mensal` in the workgroup, which is what `views.sql` already used.
- Someone who edits `transform/sql` and not dbt fails the parity test. Someone who edits dbt and not the SQL fails it too. The fix is to change dbt, then either update the legacy file or accept that the oracle has to move with it. The legacy file is not a second design.
- Docs are generated locally with `make dbt-docs`. Publishing them is the manual workflow, not a push to `main`, so a repository without Pages does not go red.
