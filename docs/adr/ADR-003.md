# ADR-003: pgoutput consumer for the operational PIX database

- Status: accepted
- Date: 2026-11-24

## Context

v0.2 reads public monthly extracts. v0.3 adds the other side of a payments platform: the operational database a direct participant would write while PIX keys move, payments settle, and disputes open. That database is the compose Postgres from v0.1. It was waiting for this slice. It is not the analytical store. DuckDB still is.

The domain is a simulation, not a DICT node. Three tables are enough to show the machinery and to join the warehouse later:

- `pix_keys`, a local key registry. `ispb` is 8 digits. `municipio_ibge` is the IBGE municipality code. `key_type` uses the `ChavesPix` literals (`CPF`, `CNPJ`, `Celular`, `e-mail`, `Aleatória`).
- `pix_transactions`, payments this institution sends or receives. `forma_iniciacao` uses the v0.2 initiation codes. `payer_ispb` and `receiver_ispb` are the two participants.
- `pix_disputes`, a short stand-in for MED (fraud, unauthorized, operational failure). It is not `EstatisticasFraudesPix` and it is not in the public extract.

The changes have to land in the raw zone as Parquet, next to the BCB partitions, so the same DuckDB runner can build a current-state table. The delivery path is Postgres logical replication to SQS on LocalStack, then a Lambda-style handler to S3. Debezium is the usual answer and it is deliberately not introduced yet.

## Decision

Capture committed row changes with the built-in `pgoutput` plugin and a Python consumer.

- Postgres starts with `wal_level=logical`, four replication slots, and `max_slot_wal_keep_size=1024` (megabytes). The migration sets `REPLICA IDENTITY FULL` on the three tables so an update or delete carries the previous row, not only the primary key. The envelope's `before` image is that row.
- A publication `pix_app` lists the three tables. A permanent logical slot `pix_app_slot` uses `pgoutput`. The consumer reads with `pg_logical_slot_peek_binary_changes` (`proto_version` 1, so changes arrive at commit) and advances the slot with `pg_replication_slot_advance` only after SQS has accepted that commit's envelopes.
- One transaction becomes one event per primary key. The committed effect is what matters: insert then update in the same transaction is one insert of the final image, insert then delete is omitted, and a delete of a row that existed before the transaction is one delete. Two commits for the same key are two events and share nothing but the key. The envelope is JSON: `op` (`insert`, `update`, `delete`), `table`, `pk`, `before`, `after`, `lsn`, `commit_ts`. Values are the plugin's text form, with timestamps normalized to UTC. `lsn` is the commit's end LSN, the position the slot advances to.
- SQS is a standard queue, `pix-cdc`. The sink writes Parquet at `raw/app/<table>/dt=YYYY-MM-DD/`, where the date is the commit timestamp in UTC. A repeat of the same `lsn` and `pk` is not written again. The handler returns `batchItemFailures` for a bad message or a failed write and still writes the rest of the batch. `cdc apply` deletes only the SQS messages the handler accepted. Neither checkpoint is exactly-once.
- The DuckDB models follow the v0.2 layers. Staging casts the text log. Intermediate keeps the latest image per id, ordered by a fixed-width hex of the LSN (`lsn_ord`), not by arrival and not by `commit_ts`. The `cur_*` marts drop deletes. They are the merge. `ispb` and `municipio_ibge` are the join keys back to `dim_instituicao` and `dim_municipio`.
- The slot does not contain rows that were committed before it was created. There is no initial snapshot. `make e2e` creates the slot, then resets and loads, so the deletes and the new rows are both in the log. A truncate is refused and does not advance the slot: it would wipe the table without a delete event per key, and the current-state model would keep the ghosts.

## Alternatives considered

- Debezium (or any Kafka Connect source) on the same publication. It solves snapshot, schema history, and the streaming replication protocol, and it is the upgrade when this domain grows past three tables or needs a second consumer that cannot share one slot. It also adds a JVM connector, a Kafka-compatible broker, and an offset topic for a local portfolio stack that already has Postgres, SQS, and a few hundred rows. The publication and the replica identity chosen here are what Debezium would use. The envelope is the same idea as its change event, with readable `op` names instead of `c`/`u`/`d`.
- The streaming replication protocol (`START_REPLICATION`) instead of peek plus `pg_replication_slot_advance`. That is what Debezium and `pg_recvlogical` speak, and it is the right shape for a process that must stay under a second of lag. The SQL interface makes the acknowledgement an explicit statement after the SQS publish, which is the guarantee this slice has to demonstrate. The cost is that the consumer polls. v0.3 can afford that.
- `wal2json` or `test_decoding`. Both are easier to print. `pgoutput` is the plugin Postgres ships for logical replication and the one Debezium's `pgoutput` connector already speaks. A later swap of the consumer does not have to swap the plugin.
- Write the operational tables straight into DuckDB, or treat Postgres as the warehouse. The compose database is the OLTP source. The analytical copy is the Parquet log plus the `cur_*` merge, which is the same raw-zone pattern as the BCB extracts.
- Emit every statement as its own event and dedupe on `lsn` + `pk`. Two statements in one transaction share a commit LSN, so the sink would keep the first and drop the committed image. Collapsing to the commit is what makes that dedupe key safe.
- Advance the slot when the Parquet write succeeds, and skip the queue. The queue is the buffer between a database connection and a Lambda-shaped writer. Acknowledging at SQS accept, and deduping at the sink, is the at-least-once path a real event source mapping has. Acknowledging only at the sink would be fewer duplicates and a consumer that cannot move until S3 is up. The slice keeps the two checkpoints separate so each failure mode is visible.

## Consequences

- Delivery is at-least-once at both hops. A crash after SQS accepts a batch and before the slot advances redelivers those commits. A crash after the Parquet put and before the SQS delete redelivers those messages. The sink's dedupe key is `(lsn, pk)` inside the commit-date partition, so the replay does not add a row. Order across keys is not a single queue FIFO. The merge does not need it: `lsn_ord` is a total order per primary key.
- A consumer that stops pinning the slot holds WAL on the Postgres disk. `max_slot_wal_keep_size` makes the local default fail the slot rather than fill the disk; the unread tail is then gone and the slot has to be recreated, which loses the position. Production needs a lag alarm before that limit, and a consumer that stays up. Dropping a slot on purpose has the same effect. This consumer cannot replay from the beginning of the table.
- There is no snapshot. Cutover of a database that already has rows needs a dump or a Debezium snapshot. Creating the slot and waiting only captures later commits. The README says to start `make cdc` before `make load`.
- `REPLICA IDENTITY FULL` writes the old row into WAL on every update and delete. That is the right trade for three narrow tables. It is the wrong trade for a wide table with large text. A future table can use the default identity if the envelope only needs the key in `before`.
- An unknown pgoutput message that is a truncate stops the consumer without advancing. Type, origin, and logical-message records are skipped. A new business table added to the publication is ignored until it is listed in `cdc/tables.py`, and its commits are still acknowledged so an extra table cannot pin the slot forever. The Parquet schema does not evolve itself.
- The `cur_*` models are a merge of a log, not a system of record. Postgres remains the place a payment is authorized. Rebuilding the DuckDB file from the log must reproduce the current tables; `make e2e` checks that. v0.5 can port the SQL to dbt the same way as the BCB models. v0.4 can point the raw views at real S3 without changing the envelopes.
- CI runs the API against a Postgres service container and runs the decoder, envelope, dedupe, and merge tests with no Docker. The service container is not `wal_level=logical`, so the replication round trip skips there. `make e2e` is the local proof against compose.
