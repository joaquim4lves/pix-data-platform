# ADR-006: Local Airflow, not MWAA

- Status: accepted
- Date: 2026-11-24

## Context

v0.4 schedules the BCB extract with EventBridge and a Lambda, and it drains CDC with an SQS event source mapping onto a second Lambda. v0.5 made dbt the transformation layer. v0.6 was the planned orchestrator. The diagram in ADR-004 already draws Airflow on the laptop and EventBridge in the account. This record is the choice of how that Airflow runs, and how a run picks a month without fighting the watermark.

MWAA is the managed Airflow service. The smallest environment is billed per hour whether or not a DAG is running. That is the same class of idle cost ADR-004 refused for NAT, RDS, and a load balancer: tens to hundreds of dollars a month for a portfolio that otherwise sits near zero. A self-managed Airflow on EC2 has the same shape. The laptop already runs Postgres and LocalStack.

Airflow 2.10 was the version the slice was first sketched against. By this release the 2.x line is end of life, and 3.4 is the supported release. astronomer-cosmos 1.16 tests Airflow 2.11 and 3.0 through 3.4. Task SLAs were removed in Airflow 3.0. Deadline Alerts, added after 3.0, are the replacement: the scheduler invokes a callback when queued-at plus an interval has passed, including when the run is still going.

Cosmos can render each dbt model as a task. The alternative is one Bash or Python task that shells out to `dbt build --select ...`. The model graph is the thing a reader opens the UI to see. A single bash task hides it. Cosmos also emits OpenLineage-style asset URIs that Airflow 3 rejects when they contain dots. The DAGs in this repo turn that emission off and publish four explicit assets instead.

DuckDB is one file. Two dbt tasks writing it at once fail on the lock. The Olinda API returns HTTP 500 often enough that the client already retries, and a fan-out of the three entities makes that worse.

## Decision

Airflow runs only in Docker, on the compose profile `airflow`. It is not in Terraform. EventBridge and the two Lambdas stay the AWS path.

- Image `apache/airflow:3.4.0-python3.12`, LocalExecutor, no Celery and no Redis. Services are the API server, the scheduler, and the DAG processor. Deadline callbacks are synchronous, so there is no triggerer.
- Metadata is a database named `airflow` on the compose Postgres, owned by a role that is not the application role. It is not in the `pix_app` publication. The application database stays `pix`.
- `bcb_pix_monthly` maps one task per Olinda entity and calls `ingestion.bcb.pipeline.run`. A scheduled run is `mode=ingest`: the watermark and the lookback window, partition overwrite, empty months left in place. Conf `start` and `end`, or `ano_mes`, is a backfill of those months. An Airflow run whose type is `backfill` uses the logical date in America/Sao_Paulo as one AnoMes. `catchup` is false. Turning it on does not replay history, because a catchup run is still type `scheduled` and a scheduled run revises the recent window. History is the conf window, or `airflow dags backfill`.
- The mapped ingest task sets `retries=3`, `retry_exponential_backoff`, and pool `olinda` (one slot unless `OLINDA_POOL_SLOTS` says otherwise). That is a second budget on top of the client's retry of HTTP 429 and 500. A retry rewrites the same partitions. A failed entity does not move its watermark.
- After the entities land, the DAG updates asset `s3://<bucket>/raw/bcb/`, then a Cosmos `DbtTaskGroup` selects `+fct_transacoes_mensal`, `+fct_transacoes_municipio`, and `+fct_chaves_pix` with tests after the models. A task then runs `dbt source freshness` for the three BCB sources and updates `dbt://pix_data_platform/bcb_marts`.
- `app_cdc_merge` is an asset-or-time schedule: minute 15 of every hour in America/Sao_Paulo, or asset `s3://<bucket>/raw/app/`. The drain calls `cdc.consumer.consume(..., once=True)` and `cdc.apply.apply_queue`. It does not emit `raw/app`, because this DAG is the consumer of that asset and emitting it would schedule itself again. It emits `dbt://pix_data_platform/cur_app` after freshness. The dbt group selects `+cur_pix_key`, `+cur_pix_transaction`, and `+cur_pix_dispute`, which is the incremental `delete+insert` path from ADR-005.
- `maintenance` checks replication-slot lag and lists `quarantine/`. A missing slot is a log alert. Lag above `AIRFLOW_VAR_CDC_SLOT_LAG_BYTES` (default 256 MiB) fails the task. Any quarantined object fails the task.
- Every DAG has an `on_failure_callback` and a deadline measured from queue time. The callback logs. If `AIRFLOW_ALERT_SLACK_WEBHOOK_URL` is set it POSTs the event name and the message. The URL is not copied into the body. There is no Slack secret in the repository.
- Connections and variables are environment variables: `AIRFLOW_CONN_PIX_POSTGRES`, `AIRFLOW_VAR_CDC_SLOT_LAG_BYTES`, and the same `POSTGRES_*`, `AWS_*`, and `S3_BUCKET` the rest of the project already reads. The Fernet key and the API JWT in `.env.example` are local placeholders for this compose file.
- dbt tasks take pool `duckdb` with one slot, shared by both DAGs, so the file has one writer. Cosmos uses `ExecutionMode.LOCAL` and `LoadMode.DBT_LS`. `enable_mock_profile` is on at parse time so an import does not open DuckDB. The task runs with `profiles.yml`.
- CI imports the DAG folder with DagBag. It does not start the compose services. `airflow dags test` is not in CI: it would execute the tasks, including Olinda.

## Alternatives considered

- MWAA, or Airflow on EC2. That contradicts ADR-004. The orchestrator would cost more than the lake it orchestrates.
- Airflow 2.10 or 2.11. 2.10 is out of support in Cosmos 1.16. 2.11 is end of life as an Airflow line. 3.4 is the current release and Deadline Alerts exist there. The cost of that choice is the execution API and a separate DAG processor, which the compose file includes.
- One `BashOperator` for `dbt build` instead of Cosmos. It is shorter and it avoids parsing dbt at DAG import. It also hides the model graph, which is the reason to put dbt in the orchestrator. Cosmos is the choice. The bash form remains a fallback if a future Cosmos release cannot parse this project: `python -m transform.dbt_main build --select <selectors>` with the same selectors in `orchestration/dbt_cmd.py`.
- Let Cosmos emit one asset per model. Airflow 3 rejects a class of those URIs. Four explicit assets are enough for the downstream edges this slice has.
- `catchup=True` mapped to the logical month for every scheduled run. The monthly schedule would then load one month and skip the three-month revision the watermark exists to do. The Lambda would keep revising and the DAG would not. Scheduled runs stay on the watermark. Backfill is opt-in.
- Run the CDC drain inside the same task that emits `raw/app`. The schedule is "asset or time". Emitting the inlet asset retriggers the DAG as soon as the drain succeeds. The hourly cron is the local driver. An external event, after `make apply` or a future producer, is how the asset edge fires.
- Put Airflow in the default `dev` extra. The install is large and it pins a wide tree. `make test` does not require it. The CI job `airflow` installs `.[dev,airflow]` and runs `make airflow-test`.

## Consequences

- `make airflow-up` builds the image and starts the profile. DAGs are paused on creation. Unpause them in the UI or they will not call Olinda.
- From inside the containers, Postgres is `postgres` and S3 is `http://localstack:4566`. The laptop `.env` that points at `localhost` is not what the containers use. The compose `environment` block sets the hostnames.
- A second writer of `data/pix.duckdb` (`make model` on the host while a dbt task runs) can lock the file. The pool only covers Airflow tasks.
- The metadata database is created by `airflow-init` against the existing Postgres volume. It does not depend on the entrypoint init scripts, which do not re-run on a volume that already exists.
- Someone who enables catchup and expects one task per historical month will not get that. The runbook shows the conf window and `dags backfill`.
- Deadline callbacks log or POST. They do not page anyone. There is no Slack app in this repository.
- The Athena target is still not what these DAGs run. They run the duckdb target. `dbt build --target athena` stays a manual deploy, as in ADR-005.
